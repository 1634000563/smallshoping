# V1 Implementation Plan — AI 原生难点优先版

## 0. 开发战略

V1 不采用“传统进销存先做完，再接 AI”的路线。

核心开发原则：**先验证最难、最有产品价值、最可能推翻架构的东西；简单功能后置。**

第一目标不是“做完整 POS”，而是尽快证明：

> 老板可以用自然语言 + 扫码/称重，让系统理解真实意图、记住上下文、调用确定性业务能力，并在本地账本中安全完成一次真实经营动作。

## 1. 第一性原理

1. 老板不学习菜单，软件学习老板。
2. AI 是主要交互入口，但不是事实源。
3. Domain Engine 是唯一业务执行入口。
4. Ledger/SQLite 是金额、库存、会员余额、欠款的事实源。
5. AI 不得直接访问 DAO/SQLite。
6. UI 是主交互的可视化确认与兜底，不是业务工作流的前提。
7. 核心业务离线可运行；AI、同步、云端故障不得阻塞营业。
8. 生鲜、五金、便利店共用同一通用商品/单位/交易底座。
9. 先做最难的端到端闭环，再扩展功能宽度。
10. 每个阶段都必须产生可验证的用户能力，而不是只产出“模块完成”。

## 2. 为什么改成难点优先

传统路线最大的风险是：投入大量时间建设商品、采购、销售、会员等页面以后，才发现 AI 原生交互无法自然嵌入；这会迫使 UI、状态、Domain、数据模型全部返工。

难点优先路线先验证五个高风险假设：

- 语音/文本是否能稳定映射到明确 Intent。
- AI 是否能使用上下文解决“刚才那个、还是昨天价格、给老张上次那些”等真实表达。
- AI 是否能只通过受控 Tool 操作 Domain。
- 一次业务动作是否能够做到幂等、可审计、可恢复。
- 同一套模型是否同时适用于“2斤土豆”和“M8×30 304 螺丝两盒”。

## 3. 阶段设计

### Phase A — 架构与最小可行闭环（001-016）
先建立最小工程、账本、商品、会话、Intent、Tool、Risk，并尽快跑通第一个完整场景：

> “卖两斤土豆。”

**Gate A：** 无 AI 也可执行同一业务动作；AI 路径只是另一种入口；账务结果完全一致。

### Phase B — 第二个真实闭环与记忆（017-028）
加入采购、称重、会员/客户、上下文、长期店铺记忆，跑通：

> “进100斤土豆，2.8元。”
> “给张姐充200。”
> “还是昨天的价格。”

**Gate B：** 多轮上下文与记忆不破坏确定性业务；不确定时主动追问。

### Phase C — 多场景压力测试（029-040）
把生鲜与五金作为两个相反压力场景，而不是在最后才“补行业适配”。重点验证单位、规格、包装、损耗、欠款、模糊表达、历史价格。

**Gate C：** 同一通用 Domain/Tool 模型同时通过生鲜与五金关键黄金案例。

### Phase D — 可靠性、迁移、设备与支付（041-052）
在核心 AI 闭环已经证明后，再完善 UI、导入导出、设备、支付、日结、性能、安全。

**Gate D：** 线上/离线、异常/恢复、真机/模拟器、支付记录/日结口径一致。

### Phase E — 发布候选（053-060）
全量评测、回归、打包、封存、开发基线冻结。

**Gate E：** APK 可安装，核心业务离线可用，AI 黄金集达标，关键账务零一致性事故。

## 4. Vertical Slice 优先规则

每个复杂任务优先采用“从输入到事实落库”的纵向切片，而不是只建设某个模块。

例如：

```text
老板说话
→ Voice/文本
→ Intent
→ Entity Resolution
→ Tool
→ Risk
→ Domain UseCase
→ Ledger
→ DB
→ 结果反馈
```

如果某个 Slice 跑通，必须证明：

- AI 路径和人工路径写入完全相同的 Domain。
- 网络关闭时，人工路径仍可完成。
- AI 不可用时可回退。
- 重试不会重复扣库存/余额。
- 每一步可追踪。

## 5. Task 固定格式

每个任务必须包含：

- 目标
- 为什么现在做
- 前置依赖
- 必读文档
- 实现范围
- 不做什么
- AI/Domain/Data 边界
- 输入与输出契约
- 测试
- 验收标准
- 完成报告

## 6. Codex 执行规则

Codex 每次只执行当前 Task；不得跨越依赖执行后续任务。

流程：

```text
读取根 AGENTS.md
→ 读取对应目录 AGENTS.md
→ 读取当前 Task
→ 读取 Task 指定 Spec/Schema
→ 检查前置任务
→ 先补测试
→ 最小实现
→ 运行测试/构建
→ Architecture Guard
→ Task Guard
→ git diff/status
→ 输出完成报告
```

## 7. V1 明确不做

- 官方微信/支付宝自动回调清算闭环
- 多店实时云同步
- ERP/完整会计
- 全品牌电子秤适配
- 在线商城
- 无人收银
- 复杂营销自动投放

这些能力必须预留扩展边界，但不能阻塞核心 AI 原生闭环。

## 8. 最终 V1 成功标准

V1 不是“页面齐全”，而是下面六句话能可靠完成：

1. “卖两斤土豆。”
2. “进100斤土豆，成本2块8，卖3块8。”
3. “给张姐充200。”
4. “还是昨天那个价格。”
5. “今天卖了多少钱？”
6. “老张上次那些螺丝再来两盒。”

以上动作必须能追溯到确定性的业务事实；AI 不确定时必须追问；无网时核心业务仍可操作。
